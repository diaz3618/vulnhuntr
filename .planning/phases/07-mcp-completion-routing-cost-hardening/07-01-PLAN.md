# Plan 07-01: Data Models + Cleanup

## Goal

Remove dead code that would double-dispatch MCP tool calls and pollute analysis
with discarded results. Extend `TokenUsage` with the fields needed to distinguish
API, provider-reported, and subscription usage in Wave 2. Add `_diagnostics` to
`FallbackLLM` so Wave 2 and the runner can surface provider-failure events without
hitting the `__getattr__` underscore guard.

These are pure foundation changes — no behavioral difference for existing users,
all new fields have backward-compatible defaults.

---

## Tasks

### Task 1: Remove orphaned MCP dispatch blocks from `_analyze_files()`

**File:** `vulnhuntr/cli/runner.py`
**Type:** modify

**Changes:**

`_analyze_files()` currently has two dead MCP dispatch blocks — one after the
initial analysis result and one inside the `for vuln_type, report in
result.findings.items()` loop. Both call `execute_tool_calls()`, discard the
results, and never feed them back into any prompt. Once the real injection lives
inside `_secondary_analysis()` (Plan 07-02), keeping these blocks would fire tool
calls a second time and throw away results.

Remove both blocks entirely. Do not leave any MCP-related code in `_analyze_files()`
— all MCP tool call handling moves to `_secondary_analysis()` in Plan 07-02.

**Block 1 to remove** (after `result = analyzer.analyze_file(py_f, files)`):

```python
        # Execute MCP tool calls from initial analysis (if any)
        if mcp_helper is not None and mcp_helper.is_active and result.initial_report.mcp_tool_calls:
            try:
                from vulnhuntr.mcp import run_async

                mcp_results = run_async(mcp_helper.execute_tool_calls(result.initial_report.mcp_tool_calls))
                log.info("MCP tool calls executed (initial)", count=len(mcp_results))
            except Exception as e:
                log.error("MCP tool execution failed (initial)", error=str(e))
```

**Block 2 to remove** (inside `for vuln_type, report in result.findings.items()`):

```python
            # Execute MCP tool calls from final report (if any)
            if mcp_helper is not None and mcp_helper.is_active and report.mcp_tool_calls:
                try:
                    from vulnhuntr.mcp import run_async

                    mcp_results = run_async(mcp_helper.execute_tool_calls(report.mcp_tool_calls))
                    log.info("MCP tool calls executed (secondary)", count=len(mcp_results))
                except Exception as e:
                    log.error("MCP tool execution failed (secondary)", error=str(e))
```

The `mcp_helper` parameter of `_analyze_files()` remains — it will be used in
Plan 07-02 when the helper is passed through to `VulnerabilityAnalyzer`. Do not
remove the parameter signature.

- `grep -n "execute_tool_calls" vulnhuntr/cli/runner.py` returns zero matches
- `grep -n "MCP tool calls executed" vulnhuntr/cli/runner.py` returns zero matches

### Task 2: Add `usage_type` and `provider_note` to `TokenUsage`

**File:** `vulnhuntr/cost_tracker.py`
**Type:** modify

**Changes:**

Add two new fields to the `TokenUsage` dataclass with defaults so all existing
construction sites remain valid (they all use keyword arguments — verified in
RESEARCH.md Q6). Update `to_dict()` and `from_dict()` to serialize/deserialize
the new fields with backward-compat fallbacks.

**Step 1 — Add import at top of file** (after existing imports):

```python
from typing import Literal
```

(Check first — `Literal` may already be imported. If so, skip. If the file uses
`from __future__ import annotations`, the import still needs to be present for
runtime use in `Literal["api", ...]`.)

**Step 2 — Add fields to `TokenUsage` dataclass** (after the existing `call_type: str = "analysis"` line):

```python
    usage_type: Literal["api", "provider_reported", "subscription"] = "api"
    provider_note: str | None = None
```

**Step 3 — Update `to_dict()`** (add two new keys at the end of the returned dict):

```python
    def to_dict(self) -> dict:
        return {
            "input_tokens": self.input_tokens,
            "output_tokens": self.output_tokens,
            "total_tokens": self.total_tokens,
            "model": self.model,
            "cost_usd": round(self.cost_usd, 6),
            "timestamp": self.timestamp.isoformat(),
            "file_path": self.file_path,
            "call_type": self.call_type,
            "usage_type": self.usage_type,
            "provider_note": self.provider_note,
        }
```

**Step 4 — Update `from_dict()`** (add backward-compat reads at the end of the `cls(...)` call):

```python
    @classmethod
    def from_dict(cls, data: dict) -> TokenUsage:
        return cls(
            input_tokens=data["input_tokens"],
            output_tokens=data["output_tokens"],
            model=data["model"],
            cost_usd=data["cost_usd"],
            timestamp=datetime.fromisoformat(data["timestamp"]),
            file_path=data.get("file_path"),
            call_type=data.get("call_type", "analysis"),
            usage_type=data.get("usage_type", "api"),
            provider_note=data.get("provider_note"),
        )
```

### Task 3: Add `_diagnostics` to `FallbackLLM.__init__`; upgrade fallback log to structured event

**File:** `vulnhuntr/llms.py`
**Type:** modify

**Changes:**

The current `FallbackLLM.__getattr__` raises `AttributeError` for any name
starting with `_`. Adding `_diagnostics` lazily (outside `__init__`) would trigger
that guard. The fix is to initialize it directly in `__init__` so it exists as a
real instance attribute before `__getattr__` is ever consulted.

**Step 1 — Ensure `Any` is imported** (verify `from typing import Any` is at the top;
it already appears in `llms.py`, so no new import needed).

**Step 2 — Add `_diagnostics` in `FallbackLLM.__init__`** (after the last existing
assignment in `__init__`):

```python
    def __init__(self, primary: LLM, fallbacks: list[LLM]) -> None:
        self._primary = primary
        self._fallbacks = fallbacks
        self._active: LLM = primary
        self._all_llms: list[LLM] = [primary] + fallbacks
        self._diagnostics: list[dict[str, Any]] = []
```

**Step 3 — Upgrade the informal fallback log message in `chat()`**.

Find the current block inside `FallbackLLM.chat()` that runs when `llm is not
self._active` (the branch that handles transferring history to the fallback).
It currently has:

```python
                    log.warning(
                        f"Primary LLM failed, falling back to {llm.model}",
                        extra={"fallback_index": i, "model": llm.model},
                    )
```

Replace it with a structured structlog event plus a diagnostics append:

```python
                    log.warning(
                        "provider_failed_falling_back",
                        failed_provider=type(self._active).__name__,
                        failed_model=getattr(self._active, "model", "unknown"),
                        fallback_provider=type(llm).__name__,
                        fallback_index=i,
                    )
                    self._diagnostics.append({
                        "failed_provider": type(self._active).__name__,
                        "error_class": "pending",
                        "failure_reason": "pending",
                        "fallback_to": type(llm).__name__,
                    })
```

**Step 4 — Move the append into the `except LLMError as e` block** so `error_class`
and `failure_reason` are available. The structured log and append both belong there:

Look for the `except LLMError as e:` block:

```python
            except LLMError as e:
                log.error(
                    f"LLM {llm.model} failed: {e}",
                    extra={"model": llm.model, "fallback_index": i},
                )
                if i == len(self._all_llms) - 1:
                    raise LLMError(
                        f"All LLMs failed (primary + {len(self._fallbacks)} fallbacks). Last error: {e}"
                    ) from e
                continue
```

The `log.warning` for "falling back" fires BEFORE the exception, in the history-sync
block. The `log.error` fires on exception. Keep both but append the diagnostic dict
only in the `except` block where `e` is available:

After the existing `log.error(...)` call inside `except LLMError as e:`, add:

```python
                self._diagnostics.append({
                    "failed_provider": type(llm).__name__,
                    "error_class": type(e).__name__,
                    "failure_reason": str(e)[:200],
                    "fallback_to": type(self._all_llms[i + 1]).__name__ if i + 1 < len(self._all_llms) else "none",
                })
```

Also upgrade the `log.error` in `except LLMError` to structured fields:

```python
                log.error(
                    "llm_failed",
                    provider=type(llm).__name__,
                    model=getattr(llm, "model", "unknown"),
                    error_class=type(e).__name__,
                    failure_reason=str(e),
                    fallback_index=i,
                )
```

And upgrade the `log.warning` in the history-sync branch to the D-18 structured form:

```python
                    log.warning(
                        "provider_failed_falling_back",
                        failed_provider=type(self._active).__name__,
                        failed_model=getattr(self._active, "model", "unknown"),
                        fallback_provider=type(llm).__name__,
                        fallback_index=i,
                    )
```

## Threat Model

**Security considerations:**

`TokenUsage.provider_note` is a free-form string stored in checkpoint files and
log output. It must not be derived from untrusted external input (e.g., raw LLM
output). At all call sites in Wave 2, the note will be a hardcoded string literal
("claude-code subscription; no per-call cost") — not user input. No sanitization
needed for the data model itself, but Wave 2 task authors must not pass
`report.analysis` or similar LLM output as the `note` value.

`FallbackLLM._diagnostics` stores `str(e)[:200]` — truncated to prevent unbounded
memory growth from error messages that embed large payloads. The 200-char cap is
sufficient for actionable diagnostics.
