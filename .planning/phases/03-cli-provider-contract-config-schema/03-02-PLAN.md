<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| YAML file → CLIPolicy fields | User-controlled YAML config values flow into CLIPolicy fields |
| CLIPolicy.workdir → subprocess cwd | workdir string from config is later used as subprocess working directory |
| CLIPolicy.overrides → provider init | Per-provider override dicts are later merged into provider __init__ kwargs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-06 | Tampering | `CLIPolicy.workdir` field | accept | `workdir` is stored as a string in config.py. The security boundary is at `CLIProviderLLM.__init__` which uses `Path(workdir).mkdir(parents=True, ...)` — this is acceptable for a developer tool where the user controls their own filesystem. Path traversal via `../` in workdir only affects the operator's own machine. |
| T-03-07 | Tampering | `CLIPolicy.overrides` dict injection | accept | Overrides are stored as raw dicts and merged at provider instantiation. They cannot reach `shell=True` because `_run_subprocess` always receives a typed `list[str]`. The overrides are used only for timeout/workdir/etc. scalar values, not command strings. |
| T-03-08 | Information Disclosure | `to_dict()` → checkpoint serialization | mitigate | `dataclasses.asdict(self.cli)` includes `workdir` but not secrets. `CLIPolicy` has no credential fields — API keys are env vars, not config. The serialized dict is stored locally in `.vulnhuntr_checkpoint/`. Acceptable risk. |
</threat_model>
